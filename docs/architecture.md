# Architecture (M4)

The PRD is authoritative for product behavior. This document records the M1–M4 implementation.

`frontend/` is a React 19 + TypeScript Vite app. Vite proxies `/api` to FastAPI so browser requests use one origin. `backend/` is a synchronous FastAPI/SQLAlchemy 2 application with Alembic migrations. PostgreSQL stores users, sessions, email tokens, rate-limit buckets, agencies, clients, projects, requests, and review access. Mailpit receives development SMTP messages.

Tailwind CSS v4 and its Vite plugin are installed for future UI work. `frontend/src/tailwind.css` is prepared but is not imported by the app; the current UI continues to use `frontend/src/style.css` only.

Owner passwords use `pwdlib` Argon2. Session and email credentials are generated with Python `secrets`; only SHA-256 digests are stored in PostgreSQL. Session cookies are HttpOnly and SameSite=Lax, Secure when configured. A separate readable CSRF cookie holds a random token bound by hash to the database session; mutating endpoints check its header and the exact configured Origin. Prelogin mutations use a short-lived CSRF cookie and the same Origin check. Owner sessions last seven days, verification links 30 minutes, reset links 15 minutes. Links are one-use; new links invalidate old links of the same purpose. Password reset revokes all owner sessions.

Rate limits use PostgreSQL atomic upserts per source address and, where known, email over 15-minute windows. The deployment reverse proxy must pass the actual client address to the app without trusting arbitrary forwarded headers. Production email provider and edge protections are M5 decisions. SMTP failures return an actionable 503; registration can leave an unverified account, and the owner can use resend verification.

Agency ownership is enforced in SQL queries using both agency ID and authenticated owner ID. A unique owner constraint permits one agency per owner, including under concurrent attempts. The API returns 404 for another owner's agency. Clients and projects derive their agency from the authenticated owner; detail, updates, deletes, and list filters constrain ownership. Foreign and missing records both return 404. An owner without an agency receives 409 with a setup instruction.

Deviations from the PRD's conceptual full model: M1 implements only the entities and UI needed now. `RateLimit` is an extra table so limits are shared across app processes without Redis. There is no deployed production configuration or external email provider in this milestone.


M2 adds migration `0002_m2` without changing M1 records. Clients have nonunique email addresses and optional companies. Projects use PostgreSQL BIGINT minor units with database range and currency checks. `(client_id, agency_id)` references the client's unique `(id, agency_id)` pair with RESTRICT deletion, so even direct SQL cannot attach a foreign client or orphan a project. Client deletion returns 409 until projects are removed. Mutations explicitly commit, roll back integrity failures, and retain Origin/CSRF checks.

The API accepts strict JSON integer `original_price_minor` values from 0 through 9007199254740991; fractions, booleans, and numeric strings are rejected. PKR, USD, GBP, and EUR use two decimal places. The frontend parses decimal text using BigInt arithmetic and checks the safe integer boundary before conversion to JSON; formatting also uses integer arithmetic. Dates require YYYY-MM-DD and permit historical agreements. UTC creation/update timestamps are returned. Baselines remain editable in M2; issuance locking belongs to M3.

M3 adds migration `0003_m3`. Existing project prices and dates initialize the new current agreed terms. Drafts hold proposed work and the project terms version seen at the last save. Issuance rejects a stale draft, snapshots all displayed commercial and contact details, locks the original baseline and client assignment, and returns a review link only once. A partial unique index enforces one pending request per project; an owner can rotate the link while preserving the snapshot. Request events are stored for the M4 history and print UI.

Owner request reads constrain agency ownership. Issue, withdrawal, expiry, and decisions lock the project then request row in PostgreSQL transactions. Reads compute effective expiry without a GET mutation; the next write persists the expiry event. Approval adds the exact integer amount and changes the current deadline once. Identical decision retries return the existing result while a valid review session remains; conflicting decisions return 409. Projects with issued requests cannot be deleted. No background worker is required.

Review links carry a random token in the URL fragment, which the browser sends in a POST body so HTTP request URLs do not contain it. PostgreSQL holds only its SHA-256 hash. Before email verification the API returns only status, expiry, and a masked address. Six-digit codes have salted Argon2 hashes, last at most ten minutes, allow five failed attempts, have a 60-second resend cooldown, and use persistent per-request/source rate limits. The separate HttpOnly review session lasts at most 30 minutes, bounded by issue expiry, and has a CSRF token; link rotation revokes earlier verification access. Mail failures return 503 and permit another send attempt. Client confirmation is on screen and can lead to the M4 print view. Migration `0004_m3_code_hash` widens code hash storage for development databases that had already applied the first M3 migration.

Lists return `{items, total}` in descending creation/ID order, with limit 1–100 (default 25) and offset 0–1000000. Projects can be filtered by a verified owned client. The owner UI uses focused auth, agency, client, and project modules and pathname navigation without a new routing dependency. The project client picker loads paginated client batches; searchable server-side selection can replace it if agencies grow large. API errors retain HTTP status and field names, 204 responses have no body, expired sessions redirect to login, and transient load errors offer retry. Creation includes a review step; deletion requires explicit confirmation.

Native local services use a dedicated user-owned PostgreSQL 18 cluster and pinned Mailpit v1.27.0, with SHA-256 verification of downloaded binaries. Loopback binds and removal of inherited Mailpit relay settings keep email local. The native database default is 55433; Compose remains optional on 5432. Cluster storage can be placed on a filesystem supporting PostgreSQL's required Unix permissions. Native helpers do not apply migrations automatically. Existing hosted CI and Compose configuration are unchanged.

M4 adds read-only owner dashboard, cross-project request list, and tenant-scoped event history endpoints without new tables or migrations. The dashboard calculates project baselines and current terms by currency separately from unexpired pending requests; approved additions are current terms minus original terms. PostgreSQL performs aggregation before amounts are sent as decimal strings of minor units, so agency totals can exceed the safe JavaScript integer range without rounding. Individual project and request money keeps the existing safe-integer JSON contract. Filters affect the request list, not the agency-wide overview. All counts and pending amounts use effective expiry without mutating rows.

Owner print pages render the frozen request snapshot and stored event history after an authenticated read. Client print pages use the existing short-lived verified review session and a token-free URL containing only the request ID; the API proposal is checked against that ID. Browser printing hides controls and shows timestamps with local timezone labels. An expired request can show its effective expiry before a write persists the corresponding event; history labels only persisted events as recorded actions. Printable records are application records, not external certifications.
